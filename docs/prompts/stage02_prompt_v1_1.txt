# OscarDP — Stage02 Prompt v1.1 / Fixed Schema v1.0

我要对一部奥斯卡电影进行 Stage02 Shot-Centric Semantic Annotation。

项目：OscarDP（Oscar Acting Dataset）。

请严格遵守我上传的 `Stage02_Spec_v1.md`（仓库路径：`docs/stage02_spec_v1.md`）。**JSON Schema 仍为 v1.0，禁止自行增删字段。** 本 Prompt v1.1 仅强化输入预检、混合字幕的来源追溯与独立验收，不改变原有语义标注任务，也不改变“一次任务覆盖整部电影”的默认工作方式。

## 输入

我会提供：

1. `Stage01_<movie_id>.json` — 镜头 ID、起止时间
2. `<movie_id>.srt` — 成片实际字幕
3. `<movie_id>.pdf` — 电影 Screenplay
4. `Stage02_Spec_v1.md` — 固定格式规范

## 新增：输入源预检（必须在 LLM 标注之前执行）

请首先使用可用的确定性代码检查 Stage01、SRT 和 screenplay 的可读性与来源可靠性，**不要以语言模型主观猜测代替解析结果**：

1. **Stage01**：验证 `movie_id`、Shot 数量、ID 唯一性与顺序、起止时间合法性和完整覆盖范围。保留 Stage01 作为所有 Shot ID/时间的权威来源。
2. **字幕真实格式**：检测 SRT 的实际文件格式及编码；即使文件名为 `.srt`，也可能包含 WebVTT / ASS 风格标记。检查字幕编号是否存在、唯一且能稳定解析；时间戳是否合法，是否存在时间逆序、零时长、空正文或明显异常。
3. **来源污染**：检查片头片尾广告、水印宣传、非剧情来源文本，以及和剧情字幕重复的 index。不能把无关广告误当作电影对白、音效或歌词。
4. **字幕与影片关系**：核对字幕时间跨度与 Stage01 时间范围，检查明显整体错位；没有视频证据时，不得擅自修正字幕时间。
5. **剧本**：确认 PDF 可读取、文本具备连续上下文，明确剧本与成片有删减或改写的可能；不要强制一一对应。

**阻断条件**：若无法确定某个 `srt_index` 唯一对应哪个字幕 Cue、字幕正文无法可靠读取，或字幕时序/版本问题使对齐不可信，暂停正式 Stage02 标注，明确列出文件、编号、影响范围及所需修复；不要在索引不可信的情况下生成完整 JSON。

**非阻断条件**：若发现孤立的空 Cue、零时长 Cue 等异常，并且能够证明其不被引用、不破坏其他 Cue 的编号和对齐，可记录为来源质量警告，继续标注已确认可靠的内容。不要因为无关的孤立异常机械地中止整部电影；若无法证明其影响范围，则须先复核。

**源文件不可变**：不得直接改写原始 SRT、Stage01 或 PDF。若使用预先审核的清理/转换版字幕，必须能够保留并核实原始 Cue 到清理版 Cue 的映射；无可靠映射时不能擅自顺序重新编号。任何清理版必须被明确指出，且保留原始源文件以供追溯。

## 核心任务

**请你亲自进行 LLM 语义理解和对齐，不要只使用 Python 文本相似度匹配。**

阅读连续的 Screenplay 和 SRT 上下文，理解：

- 对白对应关系，包括改写、删减和重排
- 角色和说话者
- 场景、地点、时间及室内外
- 剧情事件、人物互动和叙事上下文
- 剧本明确描述或上下文合理支持的 Performance Intent、Emotion、Gaze 等表演线索

Python 仅负责读取 PDF/SRT、计算时间、关联 Shot、生成与校验 JSON。

### 数据来源规则

SRT 是 `dialogue.text` 的唯一正文来源，必须保留实际台词，不能用剧本对白替换。

Screenplay 用于建立语义对应、定位剧情、辅助确定说话者和提取表演线索。

Stage01 是 Shot ID 和时间的唯一来源。

不要编造没有依据的剧情、角色或表演信息。

没有视频画面证据时，不要将剧本描述当成已发生的视觉行为，也不要推断真实的景别、镜头角度或摄影机运动。

## 新增：混合字幕 Cue 的字段分类与文本追溯

同一字幕 Cue 可能包含对白、歌词、音效/说话方式描述，或来自不同说话者的连续内容。请先依据原始 Cue 的文字和连续语境辨别各部分，再按已有 Schema 分配：

- `dialogue[].text` **只包含实际口头对白**；不能用 Screenplay 中的台词替换字幕原文。
- `song_lyrics[].text` **只包含歌词**；不得将普通对白随歌词一起复制进去。
- `sound_cues[].text` **只包含音效、环境声、独立的非对白声音提示**；不得因为原 Cue 包含音效就把整个含对白的 Cue 复制进去。
- 若 Cue 混有多种内容，允许以**连续、可证实的原文片段**分别放入相应字段；每一片段必须保留可溯源的 `srt_indices` 或 `srt_index`。不能通过文本相似度猜测片段，也不能无依据地补词、改写、拼接不相邻片段。
- 同一 SRT Cue 时间跨越多个 Shot 时，按 Spec 在所有相关 Shot 中保留相应引用；这种跨 Shot 重复是合法的，不是新台词。
- 对相邻、同一说话人的多个连续 Cue，可以按照 Spec 合并一条 Dialogue，但必须保留按原顺序排列的全部 SRT indexes；不得跨越不相关的歌词或其他角色的台词拼接。
- 同一 Cue 中两人先后讲话 **不代表 voice overlap**。只有明确证据表明语音同时重叠，才允许 `voice_overlap: true`；角色不确定用 `speaker: null`，不要猜测。
- 不要仅凭 `[music]`、`♪`、`<i>` 或 ASS 定位标记就把整段字幕归为一种类型；应识别文本片段的功能。
- 无法可靠拆分或确定归属时，不要编造：保留能确认的内容，在最终说明中提供 movie/Shot/SRT index 和待复核理由，不要在正式 JSON 中加入新的证据字段。

文本上的允许规范化只限于可解释的样式/位置标记、换行、空白和等价 Unicode 表示；**语言内容、标点和角色归属不能靠模糊匹配擅自更改。**

## 输出

使用 Shot-Centric JSON。每个 Shot 必须包含：

- `shot_id`
- `temporal`
- `dialogue`
- `narrative`
- `tags`

可选：

- `performance_cues`
- `sound_cues`
- `song_lyrics`

字段结构及类型严格按照 `Stage02_Spec_v1.md`。

不要在 Stage02 中加入 PDF page、match_evidence、screenplay_units、unassigned_subtitle_cues 或其他冗长的底层对齐记录。

`performance_cues` 必须明确区分剧本直接证据和 LLM 推断，不能声称已由视频验证。

## 处理方式（默认一次完成整部电影）

1. 先检查并读取全部输入文件，确认 `movie_id`、Stage01 的 Shot 总数与完整时间范围、SRT 编号及条数、PDF 剧本是否可读取。
2. **一次任务覆盖整部电影，从第一个 Shot 到最后一个 Shot。** 无须我手动指定每段时间，也不要每处理 10–15 分钟就停止、交付一个 part 文件并等待我发送「继续」。
3. 你可以**在内部**按连续剧情或语义场景分段理解剧本与 SRT，再把判断映射到 Stage01 Shot；分段长度由剧情与上下文决定，不规定固定分钟数。内部各段应共享人物、事件、场景和剧本/成片差异等上下文，保证跨段一致性。
4. 每个部分都必须经过**真正的 LLM 语义理解与对齐**。Python 仅负责确定性解析、时间重叠关联、JSON 组装及验证；不得使用字符串相似度或机械填充来冒充已经完成的语义理解。
5. 保留 Stage01 的全部 Shot（包括无对白和片头片尾），不更改原始镜头时间。SRT 的实际台词与原始字幕编号必须可追溯；跨 Shot 字幕按规范保留在所有重叠 Shot 中。只有可靠的剧本/上下文信息才可用于人物、场景、动作及 `performance_cues` 标注。
6. 完成后验证：Shot 数量与 ID 和 Stage01 完全一致、无重号/遗漏、Shot 时间完全一致、`srt_indices` 指向真实且唯一可识别的 SRT Cue；对话、歌词和音效文本具有原始字幕来源；混合 Cue 的分字段内容不应错误混入；字段符合 `Stage02_Spec_v1.md`；没有编造或未经视频验证的视觉事实。**如果有可运行的独立 Stage02 Validator，请对完整输出运行并根据具体 ERROR/WARNING 修正或如实标注未解决项；若当前环境无法运行 Validator，不得声称已经通过独立代码校验。**
7. **默认只交付一份完整、可下载的 `Stage02_<movie_id>.json`**，并简要报告覆盖的 Shot/时间范围、字幕数量和少量需要人工复核的歧义。不要要求我逐段确认，不要额外输出一系列 `_partNNN.json`。
8. 辅助说话者识别
对于无法通过 Screenplay 和上下文确定说话者的 SRT 对白，可在线搜索对应电影的 English SDH / Closed Captions 字幕，辅助确认角色身份。优先选择与当前电影版本匹配的字幕，不得用辅助字幕替换原始 SRT 的台词或时间。

同一条字幕包含两名说话者不代表同时说话；只有确实存在语音重叠的证据时才使用 voice_overlap: true。无法可靠确认说话者时保留 null，不要猜测。

## 新增：最终交付的确定性验证要求

交付之前尽可能通过独立、可重复执行的代码检查：

- Stage01/Stage02 的 Shot 数量、ID、顺序、起止时间是否一致。
- JSON Schema 与字段类型是否正确；可选字段为空或缺失不应误报。
- 原始字幕 Cue 编号存在且唯一；Dialogue/Song Lyrics/Sound Cue 的全文或可追溯片段来源是否匹配。
- SRT Cue 与 Shot 是否存在合理时间对应关系；合法的跨 Shot Cue 不能误判为重复。
- 是否有来源异常、混合字幕误分类和未完成的检查。
- 对具体异常给出原始证据及剩余风险；不得通过忽略错误或改写源文件制造 PASS。

**LLM 自检不能等同于 Python Validator。** 只能如实报告实际执行过的检查；任何未经脚本验证的项目应明确写作“未执行”或“待核验”。源数据有实质性问题时，应先修复来源问题，再进行完整正式标注。

### 无法一次完成时的例外

如果受输入文件可读性、上下文、处理能力或输出限制，确实无法在当前任务中完成整部电影：

- 必须如实说明已实际完成的连续 Shot ID 和时间范围、未完成范围及原因；**绝不能将未进行语义分析的 Shot 机械补齐后声称全片已完成**。
- 仅保存确实处理完成的部分为 `Stage02_<movie_id>_part001.json`（后续按实际情况编号），不得把部分结果命名为完整的 `Stage02_<movie_id>.json`。
- 不要主动把工作拆成需要我多次发送「继续」的流程；只有确实无法完成时，才说明需要怎样恢复未处理内容。

现在请检查我上传的文件，并**以一次完成整部电影为目标**开始语义对齐和 Stage02 JSON 生成。
